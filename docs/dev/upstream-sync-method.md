# 上游同步工作方法

本文规定如何评估、借鉴和引入上游变化。[同步总账](upstream-sync.md)保存连续检查点与批次索引，
[批次记录](upstream-sync/)保存具体提交、决策理由和验证证据。
仓库通用工作约定及验证门禁见 [AGENTS.md](../../AGENTS.md)，领域职责见
[应用架构](../references/application-architecture.md)及其专题导航；本文不另设一套架构或构建规范。

## 目标与基本原则

Pilot 是 Android Agent 工作台，个人域和企业域都是正式能力。同步用于修复问题、保持协议与模型兼容、
改善现有体验并补充有价值的能力，不以功能数量、代码相似度或引入比例为目标。
产品方向分化不能成为缩小评估范围的理由，也不要求跟随上游的产品结构、供应商目录和视觉体系。

上游新增与调整的行为都要评估。适用于本地的 Bug 和功能错误必须修复；四种既有线协议及新模型的正确适配
原则上引入；新工具、新特性及既有功能调整逐项评价；新增供应商默认控制扩张。
每个提交最终只能判为“重构后引入”“不引入”或“需要用户确认”，不得用“待核实”“候选”“建议关注”代替决定。
所有拟引入内容都必须完整评估，确认目标、实现和本地适配正确后才能引入。
上游已合并、已有测试或被标记为 fix，都不能代替正确性核验。

先比较上游前后行为和本地现状，再决定目标是否引入以及怎样实现。不能仅因架构不同、改动较大或涉及持久化
拒绝有价值的演进；也不能因技术上可以重写，就认定值得新增该能力。
评估深度按影响和风险安排，局部修正可以简记，但不能遗漏关键行为或未经核实就给出结论。

## 分类评估标准

### Bug 与功能错误

核实触发条件、本地可达调用链、影响与已有保护。确认本地存在同一问题后，必须纳入修复范围。
上游方案错误或不适合本地时，沿本地职责正确解决，不能因此关闭修复目标。
本地已修复或不受影响时，给出对应代码、行为测试或触发条件不成立的证据，不能只写“架构不同”。
缺复现或协议证据时继续调查；调查未完成只能记录为评估进度，不能给出最终判定。
不得把技术核实交给用户决定，也不得把未知写成不存在问题。

### 四种线协议

OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 和 Google Gemini generateContent 的
适配、修复和能力补全原则上引入，具体边界见 [Provider 协议](../references/protocol-reference.md)。
区分协议共性、特定 endpoint 的兼容差异和供应商专属行为，不把某个网关的要求推广到所有兼容服务。

按变更涉及范围核对请求参数、流式与非流式结果、终态、工具调用与结果、usage、不透明状态及历史回放。
容错不能掩盖真正错误，结果存在不能替代本地执行状态或权限判断。
即使所在提交主要新增供应商，也必须拆出通用协议修复评价；新增第五种协议则作为新能力单独评价。
官方协议、可核实的服务行为、源码与测试共同构成证据，不能仅凭 SDK 经验或上游注释推断。

### 新模型与模型识别

新模型登记、能力识别及必要参数适配原则上引入。核实型号、模态、工具与推理能力、参数限制和适用协议，
同时验证匹配规则不会误伤旧模型或把参数量、渠道后缀误当版本与能力。
未知能力不能为方便而标成支持；模型名称也不能自动改变 endpoint 或鉴权语义。

模型支持与更换模型目录来源、匹配算法、远程更新机制分别决策。
引入外部能力目录时，核对来源可靠性、同名模型的渠道差异、更新失败恢复及与用户显式配置、企业配置的优先关系，
并保留 Turn 输入捕获边界。不能以跟进模型为由一并引入未经评估的供应商配置或远程状态源。

### 供应商与专属接入

新增供应商、推荐列表、订阅登录、专属鉴权、余额或额度查询默认不扩张，避免持续增加配置、凭据生命周期、
服务适配及真实环境验证成本。有明确需求时，评估独特收益与完整维护成本后再决定。
通过已有通用协议支持一个模型，不要求新增其供应商专属集成。
已有供应商功能的错误仍按修复处理；新增搜索、语音、媒体后端也适用此边界。

### 工具新增、调整与移除

以完整任务能力评价工具，不以工具数量或当前是否已有调用者决定。新工具可以建立新的使用场景，
但必须说明模型如何选择、执行和交付结果，不能只增加一个无完整使用路径的入口。

- 能力收益：补足什么任务，改善哪些正确性、稳定性、效率或移动端体验。
- 替代关系：现有工具能否在相同环境、权限和安装条件下可靠完成，不能只说“shell 也能做”。
- 模型直接输出也是正式替代方案：比较 HTML、SVG 等内容直接生成、默认预览、继续修改和导出的完整能力。若专用工具能力更弱、增加调用与维护成本且没有足够独特收益，则不引入；已引入的也应下线。不能为了保留工具而限制直接输出能力。
- 模型使用：描述、参数、纯校验与返回值是否明确，是否增加重复选择、误调用和无效上下文。
- 用户交付：结果能否查看、继续处理、导出或供后续步骤使用，失败是否可理解和恢复。
- 执行责任：权限、副作用、取消、资源交接和持久化是否可沿本地协议实现，长期成本是否合理。

例如图表工具需评价结构化输入到原生展示与导出的整体收益；通用脚本工具需比较其轻量执行价值与已有执行环境，
不能仅凭“通用”就引入或仅凭“可替代”就删除。新增同类供应商不自动构成新增工具能力。
历史移除决定及迁移边界应保留；新用途或替代条件变化时可复评，不能因上游仍维护就自动恢复。
移除或替换工具还须保全历史结果、旧配置解析和受管配置兼容，不能留下失用的执行路径。

### 新特性与既有功能调整

所有新特性都要评价具体用户、使用场景、收益、完整流程及维护成本。需要新身份体系、执行环境或持久化
生命周期时，给出本地设计思路与依赖。能在已确定产品范围内设计的，直接判定重构后引入；
只有确实需要用户选择新增产品范围或接受取舍时，才判定需要用户确认，并给出选项与推荐。
职责可能属于 Android、Core 或 Agent Space 时，先明确分工，不能把所有能力都堆入客户端。

既有功能调整须比较调整前后行为，包括默认值、交互步骤、可发现性、可读性、能力保留和失败体验。
不能用“保持本地风格”概括排除一整组变化；视觉改版、可用性改善和错误修复分别判定。
用户反馈可以触发重审，本地旧决定不天然正确。

用户体验不降级是采用条件：不为跟随上游增加无必要的开关、手工步骤或默认关闭已可用的能力。
已存在有效配置就能工作的行为应保持，例如标题模型有效即自动生成标题，不再增加自动标题开关。
默认预览改为默认源码必须有明确产品依据；已经造成体验退步的同步应回退该行为，而非永久沿用历史决定。
替代或下线能力时保全旧数据可读性、必要的历史展示及迁移，不能以删除工具为由损坏已生成的成果。

例如 HTML/SVG 默认展示源码还是预览，应根据成果阅读与代码阅读场景、流式完成时机、手动切换和性能评价。
自动展示与资源访问权限分别设计，不能用权限边界直接推导必须默认源码。
涉及 UI 的行为变化应在实际页面验证操作与呈现，不能只检查代码和截图尺寸。

### 依赖、性能与工程调整

依赖升级、引擎替换、APK 瘦身与构建调整须确认本地收益、许可证、来源、ABI/API 兼容及维护成本。
用功能保全和实际测量核验性能收益；包体更小不能代替 PDF 提取质量、搜索召回或图像质量验证。
不机械同步上游模块拆分、格式化、开发工具、品牌、版本号及发行渠道。
混合变更中的修复和兼容目标仍应独立评估。

## 检查范围与证据

原则上每两周检查一次；上游新版本、已知修复或本地版本规划可触发提前检查。

1. 先确认授权范围、工作树与本地代码基线，保留无关改动。执行 `git fetch upstream`，记录上批冻结终点和本次具体终点 SHA。
2. 用 `git rev-list --count <start>..<end>` 核对提交数，确认起点等于上批终点。祖先或计数异常先查 shallow clone，补齐历史；确认上游重写后再记录 hash 映射。
3. 逐提交检查完整范围和语义 diff，将行为按能力组织。纯换行、生成资源与重复搬移可合并核验，不能根据标题跳过行为变化。
4. 串联同一能力的新增与后续修复，核对冻结终点最终态；本地仍保留旧实现时，中间修复仍可能适用，不能因上游替换了整套实现而遗漏。
5. 按任务阅读领域文档，沿实际入口、消费者、写入与提交、失败恢复和测试核实本地现状。文档与实现不一致时查明原因。

方案再次交付前重新 fetch；若仍属同一未实施批次，保留已有编号，追加新提交并更新冻结终点与计数，逐项完成相同评估。
用户已作出的采用、拒绝与收窄决定同步到主表、历史关联项、方案和确认清单，不能保留彼此矛盾的旧推荐。
个人域／企业域设计须逐项注明配置归属、资源来源、执行域与凭据来源、授权复验、备份和清理责任；
本地共享 Workspace 不等于个人私有资源，也不等于企业远程 Workspace。已有契约能决定的直接沿用；
新增企业字段、客户端覆盖受管配置、数据跨域归集或放宽远程内容访问时，列明当前合同缺口与选项供用户讨论，
未确认前不得写成已确定规则。通用适配器支持某能力不等于企业平台已发布或授权该能力。

## 每个提交的判定与交付格式

评估以行为为单位分析，以提交为单位交付。新增区间每个 SHA 必须出现一次，编号连续，主判定只能使用以下三项。
判定是本批是否采用的决定，不代表代码已经实施、测试或发布。

| 最终判定 | 明确含义 | 必须提供的内容 |
| --- | --- | --- |
| **重构后引入** | 决定吸收列明的目标，按本地代码与契约实施 | 本地缺口、引入和排除范围、具体重构思路、兼容与验证要求 |
| **不引入** | 本批明确不采用，无需用户再逐项批准 | 代码或产品依据；已有等价行为、没有触发路径、收益不足或维护成本不合理等具体理由 |
| **需要用户确认** | 存在无法由既有要求决定的产品范围或体验取舍，实施依赖用户选择 | 具体决策问题、明确选项、推荐选项、各选项收益与成本，以及确认后采用的方案 |

“重构后引入”统一本地化实施的命名，包含可直接复用的小修复，不要求为了名称进行无关架构重构。
若无需结构调整，明确写“沿现有某入口修改某行为，无需结构重构”，不能只写“按本地架构适配”。
“本地已覆盖”“不适用”是“不引入”的理由，不再是额外主判定；“待核实”只允许用于过程中的工作清单。
关键证据不足时继续查明，不得用“需要用户确认”让用户判断协议真伪、Bug 是否存在或代码是否正确。
确因环境无法完成必要核实，应明确列为未完成评估及具体阻碍，不能声称已交付全部最终判定。

### 重构后引入必须具体到可执行方案

每项至少说明：

1. **目标与差异**：上游修复或改善什么，本地哪条实际路径存在缺口。
2. **实施范围**：吸收哪些子行为，哪些不吸收；关联哪些后续修复或历史提交。
3. **重构思路**：修改哪些实际组件或函数，谁负责写入和提交，调用方如何消费；有取消、失败或资源交接时说明处理方式。
4. **兼容决策**：是否涉及历史数据、配置、协议或企业合同；有变化时给出迁移和旧行为保全方案，无变化可简记。
5. **验证要求**：用哪些具体场景证明目标成立与旧能力保全，不只写“补测试”或“跑全量”。

多个提交共同实现同一能力时可引用一份有编号的方案，逐提交仍需说明自己对应的范围。
方案必须足以供实施和审查，不能把核心设计全部推迟到“实施时再研究”。

### 不引入必须有可核实理由

本地已覆盖须指出等价行为与证据；不适用须指出缺少哪条触发链。
新增供应商、品牌或独立发行流程可按已确定边界直接判不引入，无需每次请用户确认。
不能仅写“架构不同”“以前跳过”“不是企业功能”“改动太大”或“没有现成调用者”。
Bug 修复目标适用于本地时，即使上游补丁错误，也必须给出本地修复方案，不能直接判不引入。
历史条件变化时可重新判断，当前不引入不等于永久否决。

### 需要用户确认必须是可回答的决定

写清用户需要选择什么，而不是笼统询问“是否引入”。例如新增独立执行环境时，
比较“本批新增该执行环境”和“保持现有执行环境”的实际能力、凭据和维护差异，给出推荐及两种结果。
普通实现细节、局部 UI 改善和已明确要求的修复由评估者决定，不扩大确认范围。
确认项不阻止其他独立且已明确项目完成评估；未经确认不实施其依赖内容。

### 混合提交与逐项记录

一个提交中的协议修复、供应商接入、UI 改版等分别作子判定，不允许用主判定隐藏排除项或未决选择。
主判定按以下顺序确定：存在需确认的子项则为“需要用户确认”；否则存在引入子项则为“重构后引入”；
所有子项均不引入才为“不引入”。需确认提交中已确定的独立修复仍可单列实施。
同一能力的后续修正可合并方案，逐提交计数不合并。

批次主表固定包含：

| 序号／提交 | 变更目标 | 最终判定 | 本地依据与子项范围 | 重构方案或不引入理由／确认问题 |
| --- | --- | --- | --- | --- |
| 每个 SHA 一行 | 比较前后行为，不只抄标题 | 三项之一 | 指向实际代码、测试或详细评估 | 引用明确方案或写出完整决定 |

详细方案与确认表放在同一批次文档内，由主表编号或文内链接定位。末尾核对三类计数之和等于冻结区间提交数，历史复评另计；
每个重构后引入项都能找到方案，每个需要确认项都能找到选项和推荐。

## 历史复评

每批接续上一批未决清单、未引入项及混合提交排除子项，核对原原因是否仍成立，
并检查新提交、用户反馈、本地能力或产品需求变化是否影响更早决定。
同一能力补齐、原拒绝理由失效、替代环境变化或发现正确性问题时，必须重新核对完整最终态。
不能只因本批没有修改该能力就忽略未决项；品牌、独立版本等原因稳定且无相关变化的项目可简记沿用依据。

历史复评采用同样三种最终判定。每项记录来源批次与提交、原决定与原因、新证据、当前决定及对应方案或确认问题。
历史补纳纳入本批实施及验证，新区间提交数与跨批补纳数分别闭合，不重算旧批次或改写历史验收事实。
本地已覆盖和已移除能力也可因新证据重审，不能把过去结论当作永久证明。

## 实施、验证与完成

实施前明确依赖顺序、修改边界、数据与兼容决策、验证矩阵及用户确认结果。
沿现有 owner 和写协议实现，必要迁移按领域契约完成；不能用旁路 metadata、第二状态源或兼容转发层规避设计。
同步模型、工具和配置时核对企业下发合同、旧版本兼容及受管只读边界。
确需变更 Core 协议时，按用户授权与对应项目协调明确方案、兼容规则和依赖；本仓库任务不改其他项目代码。

重要同步先经独立上下文复核并讨论收敛，再实施；复评内容一同审查。
所有提交及历史复评均有依据充分的三类判定后，才能宣布评估完成；需要用户确认的决定集中列出。
未完成技术调查时只报告评估进度。用户确认项未收敛前，不宣布其实施计划已确定；独立修复可单列实施。
实施后重新审查实际 diff，计划审查不能代替实现审查。子代理数量与协作范围遵循 AGENTS.md。

恢复既有体验时先查原始引入及后续调整的 Git diff，列出实际受影响的内容类型、解析路径和界面入口。
用户说“HTML/SVG 等”时不能把举例当完整范围；例如必须同时核对 Mermaid、原始 HTML、数学、表格及图片，
区分需要撤回的默认行为、未受影响的既有能力和从未支持的新能力，并将清单及验证映射写入原批次记录。

按仓库验证要求先定向再扩大，协议核对实际请求与回放，工具核对执行到交付，UI 核对真实交互，
数据变化核对迁移、事务和失败恢复。只增加保护关键行为的测试，不以静态扫描代替运行行为。
设备、外站服务和 opt-in 场景缺口如实列出，不把跳过、历史报告或仅编译通过记成本批功能验证通过。

完成须同时满足范围和分类闭合、选定代码与文档落地、风险匹配的门禁及审查完成；未决项和外部未验边界明确。
影响正确性或必要验收的缺口不能仅靠列出风险就标为完成；用户明确接受的验收例外单独记录。
提交、推送、版本号与发布按本批授权执行，计划文档提交与实现提交分别记录。

## 文档分工

需要用户确认时，先用实际操作例子说明新增能力、当前行为差异和建议，再提出真正影响产品或数据边界的决定。
用户尚未理解或认可该功能，不提前追问保留天数、存储归属等实现细节，也不将未回答的推荐写成决定。
同一种用户操作优先复用一致的能力和界面；个人、企业及文件来源的差异由已有授权入口处理，不无依据地增加功能分级和开关。

- `upstream-sync.md`：远程说明、连续冻结范围、批次状态、极简介绍与记录链接。方法调整或初步浏览不推进已完成审查检查点。
- `upstream-sync-method.md`：统一维护判定标准、评估流程、交付格式与完成门槛，不放某批具体结论。
- `upstream-sync/batch-N-YYYY-MM-DD.md`：每批唯一的完整记录，集中保存本批基线、逐提交及子项结论、历史复评、重构方案、确认选项、验证矩阵和实际证据。评估、实施与验收在同一文件持续更新，不另建该批的总览、前后分册、历史复评分册、计划或验收文件。
- `upstream-sync/phase-N-review-YYYY-MM-DD.md`：稳定检查点的范围连续性、产品边界、职责、持久化兼容与验证复核，不替代逐批记录。
- `docs/references/`：实施后的当前契约，不保存同步过程和待选方案；稳定规则引用所属专题，避免重复维护。

批次文档按阅读顺序组织：范围与结论摘要、完整的新提交主表、历史复评、具体重构方案与集中确认选项、实施及验证记录。
内容较长时使用标题、目录和文内链接导航，不按提交数量、评估者或内部任务分工拆成多个文件。
并行评估及独立复核的中间材料必须在交付前合并，消除重复和矛盾，删除临时分册并修正所有引用；
不能把“总览链接到多个分册”视为完整交付。原始日志和测试产物可作为证据引用，但不能另存一套判定或实施结论。
交付检查同时核对：本批只有一份记录、全部提交与历史范围完整、确认项及方案可在本文定位、没有遗留分册链接。

分析或实施未完成标记为 ⏳，只有满足完成门槛才能标记为 ✅。
历史证据更正写入对应详细记录及必要索引，新的复评决定记录在新批次。
本方法的分类用于后续评估，不重新解释历史批次的分类计数或验收状态。
