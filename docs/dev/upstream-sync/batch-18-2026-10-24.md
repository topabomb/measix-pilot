## 本次规则带来的具体差异

1. **适用修复不能因架构不同而拒绝。** 例如 #32 前台服务虽然没有上游引用计数，仍存在旧停止回调与新启动交错；采用本地观察代次和 startId 保护。
2. **供应商提交必须拆开看。** #74 不采用订阅账号、额度与专属鉴权，单独吸收 Responses 参数；不把它整项标为供应商而跳过。
3. **模型与目录机制分别决定。** #106 的模型匹配/精确登记引入，#107 的跨渠道投票和每日远程目录替换不引入；历史模型按官方证据补纳。
4. **行为调整不能一律随上游。** 历史 HTML/SVG 默认源码重新判定，恢复完整内容默认预览；保留源码切换、失败回退和原资源授权。
5. **已有覆盖必须指出实现。** #65 记忆空态、#69 保存提示清理、#76 空 base64 回退 URL 均已有本地路径，判不引入，避免重复做。
6. **工具按完整任务价值评价。** 历史图表、JS、画板、Skill 创建等分别复评；不再只以“shell 能替代”或“上游仍有”下结论。
7. **正确性与维护成本共同决定替换。** 自研 PDF、裁剪引擎和取消 jieba 不采用；扫码、FTS rowid 维护等采用有本地落点的方案，不照搬打包或数据初始化方式。

### 第 32 项：前台服务竞态核实

本地没有上游的 ACQUIRE/RELEASE，所以不能复制其计数逻辑。但相同 Android 生命周期风险仍可达：`serviceScope = CoroutineScope(SupervisorJob())` 的 monitor 在默认调度器读取旧的 `keepAlive=false`，主线程随后接受新的 onStartCommand 并 publishForeground，旧 monitor 再无条件 `stopSelf()`，会停止新启动需要的服务；或 stop 发生在系统已收到、应用尚未处理下一次 start 之间。代码允许该交错，本次未声称设备复现崩溃。

[Android Service 文档](https://developer.android.com/reference/android/app/Service#stopSelf(int))规定带 startId 的停止只对应最后一次已知启动请求。仅把 stopSelf 改成“当前最新 startId”仍会让旧 false 停掉新启动；必须保留观察所捕获的启动代次，并在新 start 时废弃旧观察。Main 串行化解决本地跨线程交错，startId 解决系统已排队的新启动，二者都需要。已有 timeout 使用 startId，应继续保留。权限拒绝路径也要在相同生命周期串行边界处理，保留诊断而不伪造 Turn 失败。

### 第 44 项：Claude 搜索协议核实

本地 Claude capability 是 BASIC，`ClaudeProvider` 未编码 `web_search`/`server_tool_use`，因此上游的选择器放开不是本地可直接接受的完整功能。官方 [Web search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) 的基础请求为 tools 中 `type=web_search_20250305,name=web_search`，可带 max_uses；回包包含服务端调用、搜索结果、引用，也可能包含搜索错误。先实现基础版本，不默认扩张动态过滤代码执行。

按官方 [Server tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/server-tools)，server_tool_use 与 web_search_tool_result 通过 tool_use_id 配对，服务端执行，无需客户端补 tool_result；与客户端工具并行时可能延期，pause_turn 需要保留 assistant 内容继续请求。这要求本地完整保留内容顺序及不透明数据，并区分客户端待执行工具与服务器结果。实施测试必须覆盖普通/流式块合并、引用位置、错误 max_uses_exceeded、pause_turn、混合调用、历史重放、取消、usage 累计与最后请求统计；不能只增加一个 Boolean。

**续传接入执行链**：当前 `claudeStopReasonError` 将 pause_turn 判为 INCOMPLETE；仅取消该错误也不够，`StepRunner.run` 在没有本地待执行工具时直接返回 Final，`TurnRunner` 随即结束 Turn。Provider 必须返回明确的协议续传结果，经 `StepModelResult` 的缺省兼容类型化字段保存，不由 app 猜测任意 finishReason。增加 `StepExecutionResult.ContinueSampling`（拟名）：无本地待执行工具且协议要求续传时，经 `TurnRunState.commitModelResponse` / `ModelResponseCheckpoint` 在同一事务保存完整服务端块、usage、回放证据，闭合本 Step 为 Continue 并打开下一 Step；提交成功才发布及请求下一次采样。`TurnTransition.advanceCompletedToolStep` 当前对空工具列表直接返回，须按真实的工具完成或协议续传条件合并为明确的采样推进方法，并移除被替换的旧命名/路径。

`TurnRunner` 对该结果跳过 ToolBatchRunner，在原 TurnHandle 下继续；混合客户端工具仍先走原参数校验、审批和执行，同 Step 完成后才续传，不能绕过等待交互。每次续传计入原 maxSteps，通过下一 Step 的 `TurnRequestAdmission` 复验权限和接纳请求，达到上限保留证据并给出明确原因，不增加用户开关、不当作网络失败自动重试，也不创建新 START。取消、断流、未知 stop reason 仍沿失败/取消协议，不能据此续传；事务失败不得发出后续请求。验证纯服务端连续 pause_turn、混合工具审批、达到上限、checkpoint 失败、撤权与取消；旧 Step 无新增字段保持原语义，进程恢复不自动恢复网络执行。

**服务端块与终帧合并**：为服务端调用/结果增加 `UIMessagePart.ServerTool`（拟名）的只读协议片段，保存协议来源、有序块身份和原始块；它不属于 `UIMessagePart.Tool`，不进入审批、ToolBatchRunner 或本地执行记录，也不伪装 Reasoning 或空 Text。`ClaudeProvider` 的 input_json_delta 按原 content block 类型路由，服务端 input 只能更新该片段，不能产生本地 Tool。普通文本仍用 Text，引用按所属文本块保存并投影。新增片段同步更新 ModelRequestMessage 转换、持久化序列化、上传有效性、UI 和搜索投影：仅有完整服务端块的响应仍有效，但原始 JSON 不作为正文或 FTS 内容。旧数据缺该类型不改变原行为。

流式合并区分正文增量与完整块终帧：前者追加正文，后者按 responseId/index 替换完成后的原始块、补齐引用与不透明字段，不再次追加已有正文。现有 `StepOutputAccumulator.mergeContentBlock` 的 Text 分支必须合并类型化 metadata，不能只拼 text；服务端片段增加明确的合并分支。完整已提交 Step 才能回放服务端原始块，`replaySafeTailParts` 明确剔除未完成尾部的该类型，取消、错误与恢复不得通过默认 else 保留不完整协议状态；端点/协议切换不得原样发送不兼容块。测试仅服务端块的 pause_turn、引用晚于正文、完整终帧重复、断流尾部、跨端点及混合客户端工具。

**P74 与媒体插入共用的槽位规则**：保留 `ProviderContentBlockSlot` 作为响应内稳定身份，不将当前列表位置当身份。`StepOutputAccumulator` 所有前插统一经过内部插入函数，插入时同步平移 `contentIndices` 中该位置及之后的下标；Tool 追加不需要平移，Step 切换清空槽位表。禁止各分支另行插入而不维护映射，后续完整块更新仍按槽位定位。此修改同时覆盖 Responses 图片和文本/工具交错，验证“正文→客户端工具→有槽位正文→图片前插→后续正文增量”及多次插入，检查正文不丢、不串块、最终顺序与回放一致。

### 统一图片规则与窄标注

P70 与历史画板项只实现发送前预览、缩放平移、自由画线、圆/矩形/箭头、颜色/粗细、撤销/重做、取消/完成。不开空白画布，不增加文字、编号、脱敏涂抹、图层、对象选择、压力笔或可编辑工程文件；不引入 Ink alpha。完成后合成平面图片，再次打开只能继续标注，不能编辑之前已合成的形状。

复用 FileEncoder 既有 EXIF 校正、1600 万解码像素预算、最长边 2560、不放大、WebP Q90 和透明度规则。标注输出暂存无损 PNG，模型请求仍由 FileEncoder 统一编码，避免两次有损压缩。编辑后的 MCP 原图成为新的本地图片，不继承 preserveOriginal；GIF 保留原动图预览/发送，本批不提供动图标注。

FileEncoder 的 compressAndEncode/normalizeByExif/applyExifTransform 当前是 private；在 `ai` 提取受控的静态像素准备入口（拟名 `withPreparedStaticImage`），由原编码和 app 标注合成共用，统一方向、解码预算、缩放及 finally 回收 Bitmap。返回/借用的是规范化像素，不携带 Artifact、空间或 UI 状态；app 在该回调内绘制并输出无损 PNG。不得先调用 encodeImageBytes 再解码为画布，否则已提前做 WebP 有损编码。沿原编码入口验证新旧输出等价，再接标注，不复制另一套 EXIF/缩放参数。

ArtifactDraftScope 绑定原 ConversationCommandTarget，负责授权读取及结果接纳，ArtifactStore 仍唯一管理附件。ChatVM 编排，UI 只持编辑状态；捕获 inputIdentity、附件 identity 和原视图，完成时条件替换，不能按 URI 或列表位置覆盖。保存期间发生发送、删除重选、切域、登出或取消，迟到结果只清理本操作的新资源；已发布历史附件不得删除。验证 EXIF、透明大图、缩放坐标、GIF/MCP 编码、重复 URI、发送竞态和撤权，真机触控单列验收。

### Q1 发送队列及停止修复

对应历史 66de8b30 与 #116，用户已确认引入。首版保持上游的进程内队列范围，不增加 Room 队列表、后台调度系统或跨进程恢复承诺。输入框运行期间仍可编辑并点发送，待发列表展示顺序及附件，支持编辑、撤回；编辑队首时阻止它出队，后续项不能越过。队列为空仍走原发送体验，不新增全局开关。

1. **状态与入口**：队列作为 ConversationRuntime 的临时输入状态，由 ConversationTurnService 的类型化 enqueue/edit/remove/resume 命令管理；ConversationPresentation/query 只投影队列 UI。每项保存稳定 itemId、不可变输入、answer、原会话/空间/Session 身份及附件所有权，不新增可编辑会话副本。ChatVM 只在 enqueue 成功交接后清空对应 inputIdentity，失败保留草稿。
2. **不会打断当前轮**：现有 startRequest 会 installAndStartTurnWorker 并 supersede 旧轮，不能重复调用它实现排队。在原 Runtime/Registry 安装边界增加“仅空闲时接纳队首”的原子分支，复用会话操作锁；检查活动 worker 已退出、stream 已终结、执行租约释放，审批/提问等待不是空闲。只有接纳成功才将 item 标为提交中，不由 UI 的 isGenerating 或定时器驱动。回复正常完成后从服务端终态处理调用下一次调度。
3. **提交与失败**：出队沿原 AppendUserMessage、Draft 首发晋升、TurnCommitter 链；START 时捕获当前有效配置，入队时不冻结未来 Turn 的模型/System。使用稳定 userMessageId 核对提交结果；提交前失败回到待发且暂停，保留原输入和附件以便修正后重试。提交成功即移出待发，后续模型失败只暂停余项，不能重新追加已提交用户消息；已提交但回执取消也按持久结果对账。审批回答继续原 TurnHandle，不能消耗下一项。显式重试/编辑重发优先处理当前轮，余项暂停，不自动串到错误分支。
4. **停止竞态**：stop 在同一调度锁内先设置 paused 并递增 dispatchEpoch，再捕获/取消活动 worker；取消等待在锁外执行，避免 join 死锁。完成回调必须核对 epoch 和当前所有者，不能在 stop 之后启动下一项；已成功安装的 worker 纳入 stop 范围。停止完成仍要求原任务与资源实际退出，手动恢复才重新调度，不因新入队一条就自动解除暂停。
5. **附件交接**：扩展现有 ArtifactDraftScope/ArtifactSubmission 的类型化移交，入队时由队列保管创建权和引用 pin，导航销毁输入组件不得回收队列附件。实际提交使用已接管的 submission，不对同一资源重复 claim；成功事务后 publishCommittedReferences。编辑先取得新附件所有权，条件更新成功后再释放本项不再引用的旧资源；撤回只释放本项所有权，其他待发项/已发布历史仍引用的资源保持。复用 ArtifactStore，不通过 URI 或全盘扫描推断可删除文件。
6. **页面、空间与进程**：离开聊天页面保留进程内待发队列，服务所有者继续管理，不能持有已关闭的 UI CommandTarget 来执行；由原接纳的会话及 Session 身份派生执行租约，出队复验，不借当前页面重新绑定。切域暂停原域尚未发出的项，回原域显式恢复；只切换聊天不改变来源。登出/撤权/删会话终止原域队列并释放未发布资源，已提交消息沿原删除/恢复链。显式清空或退出涉及待发内容时提示数量和损失；进程被系统终止不自动重发，界面说明待发项未发送且只在本次运行保留。未发布附件遗留仍由既有启动恢复清理，不假称队列已恢复。
7. **验证**：覆盖 A 运行时 B/C 入队并各提交一次；队首编辑、撤回和重复附件；审批继续不触发下一轮；提交前失败、提交后回执取消、模型失败；stop 与完成/出队的每种锁顺序；双击发送与首发晋升；切聊天、切域、登出重登、撤权、删除、进程重建；与标注保存同时发生时 inputIdentity 不串项。定向行为测试后，用专用设备验证列表/键盘、待发编辑、附件和停止交互。

**调度通知的准确时机**：releaseTurnWorker 在旧 worker 的 finally 中清理租约并移除 Runtime 引用，此时旧 Job 未必 completed。队列保留上一 dispatch Job，invokeOnCompletion 仅向 appScope 投递一次调度请求；调度者在锁外确认旧 Job 与资源结束，再进入原操作锁复验 epoch、队首版本、授权和 idle 条件，不在旧 worker 内 join 自己，也不因提前看到 currentWorker=null 就启动。startRequest 会捕获部分异常并正常结束 Job，因此新增内部类型化完成结果（提交前拒绝／已提交正常完成／等待交互／已提交失败／取消），由原 Turn 终态及稳定 userMessageId 对账产生，不以 Throwable==null 判断可继续。通知仅触发调度，不是第二份可编辑执行状态。测试必须覆盖 worker 引用已移除但 finally 尚未返回，以及异常被捕获后 Job 正常结束仍暂停余项。

队列项另绑定原助手与分支语境；修改历史分支或移动助手先暂停，不把待发内容静默投递到新语境。编辑使用 itemId/version 比较，出队后不可再改该副本。队列持有独立只读附件访问能力，不能继续使用已移交创建 pin 的输入草稿预览。`stopEnterpriseWork`、`requireEnterpriseStopped`、Runtime 空闲逐出及 cleanup、会话删除与数据重置都须纳入队列资源：有待发项时保持 Runtime 的所属租约，显式关闭先阻止调度并释放资源，不能仅检查 worker 或静默逐出含未发内容的 Runtime。上述锁与生命周期规则用行为测试验证，不新增第二套持久化状态机。
