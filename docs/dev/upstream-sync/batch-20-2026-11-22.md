[Android 通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

验证 API 32 无运行时入口，API 33+ 拒绝后重试、永久拒绝跳系统设置、恢复授权后动作消失及运行中撤销；
复核开关关闭时无催促，以及当地语言下可看到完成提醒的授权效果。沿原 UI 架构记录入口。

### P2 长会话概览的主线程开销（#13）

把 `ChatOverview` 的现有 `projectChatOverview` 从 `remember` 移到一个由页面取消的 Compose effect，使用 `Dispatchers.Default`
计算，合并密集的节点更新。按会话、分支及搜索输入复核结果，离页或换查询时取消原工作。整条正文仍可搜索，
只限制已经送给卡片排版的片段，超长搜索词也不能扩大排版范围。首次结果到达后复用现有锚点，流式刷新不反复定位。

保持现有卡片分组、稳定 ID、附件数和收藏标识。采用一个投影响应路径，排除独立索引、派生缓存和 #42 的摘要卡。
扩展 `OverviewProjectionTest` 核对长句末尾命中、超长查询和原分组；用现有长会话工作负载对比首次打开、搜索与滑动，
设备复核流中换查询、分支切换、返回阅读位置。以实测判断收益，不从调度方式推导性能结果。

### P3 快捷消息按行追加（#17）

只在 `PromptPresetButton` 的原快捷消息点击动作处理拼接。空草稿填入模板，已有正文且未以换行结尾时插一个换行，

验证空白、多行、已有换行、附件并存及原输入许可过期，单击只编辑草稿。

### P4 模型目录刷新与 Google 缺省显示名（#18/#54）

保留 `ProviderSettingsVM.loadModelCatalog`、`ProviderSettingsApplicationService.listModels` 及现有 `UiState`。

### P5 原生 Mistral 思考回放（#19）

[Mistral Chat Completions 推理文档](https://docs.mistral.ai/inference/conversations/reasoning)

- 让 `OpenAIEndpointProfile.resolveChatReasoningReplayPolicy` 负责原生 `api.mistral.ai` 的可见思考编码形状。
  `ChatCompletionsAPI` 在原 assistant envelope 中按已提交的 Part 和 tool batch 顺序输出 `thinking[].text` 与正文 text chunk，
  `tool_calls`／`tool` 的分发仍在原边界。不以模型名触发第三方网关的线协议，不借机改参数推断。
- 让流式和非流式的 content 数组解析共用形状解析，保全每个 thinking 的有效内层文本、过渡帧和既有文本／refusal／工具字段。
  沿现有 accumulator slot 处理片段，确定可辨认的消息原序；未支持对象保留现有诊断边界。既有可见 Reasoning 文本可直接编码为
  原生格式，仍遵守 `includeHistoryReasoning` 和来源策略，兼容通用 Chat、OpenRouter opaque、DeepSeek 与 MiMo 的现有线形。
- 先用 `:ai` 和 `:app` 的本地响应夹具验证多轮、流中 `thinking + text` 和非流多块、同轮工具续接、只有文本与禁回放、同型号不同 host。
  对比第二次完整 JSON 与旧 Settings、旧历史；真实 Mistral 原生服务验证第二次调用状态和正文，记录未接入的环境边界。
  更新 [Provider 协议](../../references/protocol-reference.md)，无配置和存储迁移。

### P6 Gemini 独立签名、混排回归与 Carbon 登记（#31–33）

**修复依据。** 上游缺陷报告包含 Vertex AI 官方直连复现：Gemini 4 Argon 和 Carbon 可在正文之后发送只有 `thoughtSignature` 的末尾片段，
导致生成报错。Pilot 的流式与非流式解析共用 `GoogleProvider.parseMessagePart`，该输入会落入未知字段异常；本地现有分支已支持显式空
`text` 加签名。Google 要求保留签名，文档与现有夹具尚未证明服务端会区别处理省略 `text` 与显式 `text: ""` 的回放。
[上游缺陷报告](https://github.com/rikkahub/rikkahub/issues/2316) [Gemini 签名与回放](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures)

**最小适配。** 在 `parseMessagePart` 识别只含有效 `thoughtSignature` 的 Part，转换为现有的 `UIMessagePart.Text` 空正文部件，
用既有 `GoogleThoughtMetadata` 保存签名、模型与 endpoint 来源。`GoogleContentState` 为带签名部件分配独立 slot，
`GoogleProvider.buildContents` 沿 `samplingPartCounts` 和原来源校验回放，候选方案的发出形态为同一独立 Part 上的
`text: ""` 和原签名。保持旧消息解码、签名所属 Part、工具批次顺序和其他未知形状的诊断。若空文本会生成气泡，
只在原分组入口跳过空文本显示。来源不匹配的签名仍须剥离，通用空消息过滤和 Turn 提交仍沿原实现。

**持久化决定。** 本批采用方案复用已有空文本及签名字段，移除原拟新增的“是否省略 `text`”标记。
新识别的签名进入已有消息字段和原提交链，历史消息依原规则读取，无新增字段、全量改写或旧数据兼容分支。

**回归与验收。** #32 的录制包含先调用本地函数、再接续 Google Search 及末尾显式空文本签名，两条 trace 均未覆盖裸签名。
本地 `GoogleServerToolTest` 与 `GoogleToolReplayIntegrationTest` 已覆盖工具混排顺序、签名来源和持久化往返。
复用这些测试，只补尾部签名与裸签名的流、非流输入，核对终止状态与用量保留、落盘重读后的第二个请求、Part 的签名值和位置、
工具 ID、来源不符及未知形状仍失败。同步核对现有消息渲染分组只生成可见正文块，签名仍通过原消息字段保存和回放。上游完整 trace、录制和回放框架不引入。

在 Vertex AI 官方 `generateContent` 用同一模型与 endpoint 取得真实裸签名后，继续发送下一轮，核对服务端是否接受含
`text: ""` 的签名 Part，同时确认本轮终态和下一轮结果。可先用已接入的 Argon 验证，签名修复不依赖 Carbon 登记。

## 产品取舍

### 轮后自动摘要本批暂缓（#10/#12/#26）

用户决定本批暂不考虑自动摘要。手动摘要和已消费工具结果的 rolling compaction 照常运行，长文本超限沿原 Provider 诊断和引导处理。

### 手机共享目录挂载排除（#38）

用户明确无需上游在 `fab0c077d` 新增的共享目录挂载。该方案会把目录授权、外部卷映射与 PRoot/PTY 执行长期绑定；
即使只保留逐目录只读，仍需持久维护授权、处理撤销并限制进程访问，因此先前讨论的低权限替代也从本批移除。
本地 Workspace 继续由用户选择文件导入副本或选择本次导出的目标。`WorkspaceApplicationService` 与系统文件选择器承担原操作，
企业远程文件继续经 `RemoteWorkspaceService` 使用原 Session。[Workspace 文件与导出契约](../../references/workspace-architecture.md)
